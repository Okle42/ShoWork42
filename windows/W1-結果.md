## Windows Terminal：選了哪個做法、為什麼

實測（WT 1.24）發現比交接裡三個候選都簡單、而且不碰標題的路：

- `AttachConsole(claude 的 pid) → GetConsoleWindow()` 在 WT 裡拿到的是 ConPTY 的 `PseudoConsoleWindow`，
  **它的 owner（`GetWindow(h, GW_OWNER)`）就是目前裝著這個分頁的 WT 視窗**（`CASCADIA_HOSTING_WINDOW_CLASS`）。
  WT 為了讓主控台程式跳的對話框能對齊，會把假視窗掛到自己的視窗底下，分頁拖到別的視窗時也會重新掛。
- 實測：同一個 WindowsTerminal.exe 行程裡開兩個 WT 視窗、其中一個有兩個分頁 → 兩個分頁的 owner 都是那個測試視窗、
  跟 Kang 原本的 WT 視窗不同。**多視窗、背景分頁都對得到**，所以直接照 Mac 規則：視窗取所有分頁裡最急的狀態。
- owner 每 250 ms 重新讀一次（便宜的 `GetWindow`），分頁被拖到另一個視窗時光暈會跟過去。
- 對不到（沒有 owner、不是 WT 也不是 conhost，例如 VS Code 內建終端機）一律不亮，不會亮錯。
- 候選 2（改標題探針）完全沒用到；候選 3（UI Automation）也不需要。

**唯一做不到跟 Mac 一樣精準的地方：「哪個分頁在畫面上」。** 每個分頁的假視窗都回報 visible，分不出作用中分頁。
清除綠色時用唯讀的標題比對：WT 視窗標題 = 作用中分頁的標題，ConPTY 記得每個分頁自己的標題。

| 情況 | 結果 |
|---|---|
| 視窗只有一個分頁（最常見） | 按鍵／點擊直接清綠 |
| 視窗標題 = 這個分頁的標題 | 清綠 |
| 視窗標題 = 別的分頁的標題、不是這個分頁的 | 保留綠（在背景） |
| 誰都比不上（手動改過分頁名稱、`suppressApplicationTitle`） | 當作作用中，清綠（作用中分頁一定對；背景分頁可能被提早清掉） |

限制：同一個分頁切成多個窗格時，只有有焦點的窗格算「在畫面上」，另一個窗格的綠要點進去才會清。

## 做法摘要

- `showork.exe`：從父行程鏈往上找 `claude.exe`（檢查父行程比子行程早建立，防 pid 重用），送一行 JSON。
  pipe 不存在立刻結束；忙碌時 `WaitNamedPipe` 等剩餘時間；另有 190 ms 硬期限執行緒。永遠 exit 0、不讀 stdin。
  以 `SECURITY_IDENTIFICATION` 開 pipe，佔用名字的人也不能冒用我們的身分。
- 附著別人的主控台（拿主控台視窗、讀標題）一律在 `showork.exe console <pid>…` 子行程做，agent 本身不 `AttachConsole`：
  附著期間使用者按 Ctrl+C 或關分頁會把附著者一起帶走。
- agent：`FirstPipeInstance` 同時防重複啟動與搶名；AI 行程結束用 kernel wait 立即收掉（不輪詢）；
  `state.json` 讓 agent 重啟（系統匣「重新載入」）不失憶；WinEvent hooks 與 250 ms 看門狗只在有光暈時才開。
- 清除：low-level 鍵盤／滑鼠 hook **只在有綠的時候才裝**，回呼只記下視窗就返回；只看事件種類與目標視窗，不看按了哪個鍵。
- 系統匣：最急狀態的顏色圓點＋數量，提示文字列出各狀態數量，選單「重新載入」「結束」。

## Hooks 對應

| Claude 事件 | matcher | 送出 | 同步／非同步 |
|---|---|---|---|
| UserPromptSubmit | | working | async |
| PreToolUse | `AskUserQuestion` | input | 同步 |
| PreToolUse | `^(?!AskUserQuestion$).*` | working | async |
| PermissionRequest | | input | 同步 |
| PostToolUse | `*` | working | async |
| Stop | | done | 同步 |
| Notification | `permission_prompt\|elicitation_dialog` | input | 同步（備援） |
| SessionEnd | | clear | 同步 |

- 照 Mac 09-28 修法：AskUserQuestion 的 PreToolUse 直接紅；萬用 working 用負向前瞻排除它。
  已讀 Claude Code 2.1.283 的 matcher 實作確認：只含英數與 `|` 的字串走精確比對，其他走 `new RegExp(m).test(工具名)`，
  也會拿工具的舊名稱別名去比；AskUserQuestion 沒有別名，所以排除是完整的。
- **紅色延遲（交接要求實測）：Windows 上權限提示的 Notification 也晚約 6 秒**（Mac 說權限提示沒有延遲，Windows 不一樣）。
  實測：對話框出現 → `permission_prompt` Notification hook 觸發 5.97–6.3 秒；`elicitation_dialog` 5.98–6.00 秒。
  所以一併改接 **PermissionRequest**（對話框打開時就觸發）：對話框出現 → 紅 0.16–0.20 秒。
  Notification 留著當備援：6 秒內回答的話它根本不會來（實測回答後等 12 秒都沒有），不會晚到把紫蓋回紅。
- **跟 Mac 不同：working 三個 hook 改 async。** Windows 上 Claude 用 Git Bash 執行 hook，bash 本身啟動約 0.1 秒，
  加上 .NET exe 啟動，一個 hook 約 0.2 秒；每個工具呼叫有 Pre＋Post 兩個，同步的話每次工具呼叫多 ~0.4 秒。
  async 之後 Claude 不等它們。亂序的風險用時間戳處理：showork 附上「Claude 為這個 hook 開的行程（bash）的建立時間」，
  agent 丟掉比已套用事件還舊的事件（例如 Stop 之後才到的 PostToolUse working 不會把綠蓋回紫）。
  綠／紅／清除維持同步，跟 Mac 一樣。e2e 裡沒有發生亂序（丟掉 0 個），但機制在。
- 指令路徑用正斜線並加引號（使用者目錄有空格；反斜線對 bash 是跳脫字元）。已用 Git Bash 實測可執行、exit 0。

## 還沒做／建議

- showork.exe 啟動約 70 ms 是 .NET runtime 本身（ReadyToRun 試過沒有差別）。改成 NativeAOT 可降到 ~10 ms，
  hook 就只剩 Git Bash 本身的 0.1 秒，綠／紅也可以快 0.1 秒。但要安裝 Visual Studio Build Tools（C++ 工作負載）——
  依規矩沒有擅自安裝，等 Kang 決定。
- 分頁切成多個窗格時，只有有焦點的窗格算「在畫面上」（見上）。
- 光暈在全螢幕視窗時的「螢幕邊緣細光」（Mac 的 EdgeGlow）還沒做，不在 W1 範圍。
- `CLAUDE_CODE_*` 環境變數：從一個 Claude 裡面開另一個 Claude 時會繼承「子工作階段」標記；e2e 開測試 Claude 前會清掉。
